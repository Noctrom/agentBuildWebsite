# V0.76 — Performance check across all pages (2026-10-17)
**Agent:** dev-1
**Branch:** story/v0.76-performance-check · **Status:** done

**What I did**
- **Every route, both widths, 1× and 4×, on the production build:** measured fps, frame time, main-thread busy % and the share of frames over 35 ms. Table 1 below.
  - **Real GPU (RX 7800 XT through D3D12):** every page holds 60 fps at 375 and 1280, at 1× and at 4×, with 0% of frames over 35 ms. The main thread is 2–6% busy at 1× and 6–22% at 4×.
  - **Software raster (SwiftShader):** every page holds 60 fps at 375 (both throttles) and at 1280 1×. At 1280 4× it drops to 24–37 fps.
- **Both paths, labelled:** every run printed the WebGL renderer string. GPU runs report `ANGLE (Microsoft Corporation, D3D12 (AMD Radeon RX 7800 XT))`. Software runs report `SwiftShader Device (Subzero)`. All measured runs had the Animation switch on, so auto-pause couldn't stop a scene mid-measurement.
- **putImageData stall:** no route shows the every-third-frame stall on the GPU path.
  - Projects (`planets.ts` uploads one gas slice per frame) holds 60.0 fps with p95 16.8 ms at 4×.
  - In the other scenes, `putImageData` runs only during the build (`nebula.ts`, `sun.ts`, `galaxyBand.ts`, `starfield.ts`) or once per cached sprite (`blackHole.ts`). None runs per frame.
- **1280 at 4× ≈ 10 fps explained:** it is the test setup, not the page's JavaScript. Two causes stack up:
  - Software raster of the 1280×800 canvas runs on the throttled main thread.
  - The Windows host slowed down while I was measuring.
  - Details under "How I did it". On the GPU path the same case runs at 60 fps.
- **Auto-pause:** it triggers only on the software path, at 1280 with 4× throttle: About, Contact and Behind the Scenes in 2 of 2 runs, Projects in 1 of 2, about 6.1–6.7 s after load.
  - It never triggers at 375 or at 1×, and never on the GPU path.
  - During the slow host period it triggered on all 7 pages at 1280 4× (software).
- **The two start-up long tasks (V0.75)** are found and explained. A third, bigger task exists only on Projects. Each one can be split or shortened; see "Start-up long tasks" and the recommendations.
- **No code changed.** This log is the only file in the story.

- **Task 1 (≈ 115–150 ms, starting 60–90 ms after navigation) evaluates the single JS bundle** (`v8.evaluateModule`). CPU profile of an unminified build at 4×, split by source module:
  - **About 30% of the task:** `projectTags` in `src/content/projects.ts`. It sorts with `localeCompare`, and the first call loads ICU's collator. On a blank page that first sort alone costs 6–8 ms at 1× and about 40 ms at 4×; the second sort costs 0.1 ms.
  - **About 25%:** React / ReactDOM / router module set-up.
  - **About 18%:** the bundler runtime.
  - **The rest:** `createRoot`, React's event listener set-up and `syncMotionAttribute`.
  - **Scene modules: under 1%,** so splitting the scenes into their own chunk would barely shorten this task.
- **Task 2 (≈ 100–185 ms, starting 180–250 ms) is React's first render and commit** (one scheduler task).
  - **About 40% is the page's first style recalc and layout.** NavButton's `useLayoutEffect` forces it synchronously by calling `getBoundingClientRect` for `--expanded-w`. That layout would happen anyway before the first paint; it just lands inside this task.
  - **At 1280, `publishRailWidth` then writes `--rail-width` on `<html>`.** That triggers a second whole-document style recalc (159 elements, about 26 ms in a slow-host trace, roughly 10% of the task). The six `--expanded-w` writes only restyle 3 elements each and are cheap.
  - **The rest is React rendering the page tree.**
- **Projects task 3 (170–510 ms) is the gas giant's band texture** (`paintGasTexture` in `planets.ts`).
  - The texture is drawn on a GPU canvas with a few thousand paths, then read back with `getImageData`. The readback makes the main thread wait for all of that drawing at once, in one step of the incremental build.
  - It only happens on the first Projects visit, because the texture is cached for the session. It is the longest main-thread freeze on the site.
- **Smaller ones:**
  - Contact's galaxy build: the first step builds starfield, star seeds, glow and soft dots without yielding, and `paintBand` steps run 50–80 ms.
  - Behind the Scenes: 50–65 ms.
  - The starfield cloud bakes (V0.75) stay under 50 ms at normal speed.
- **Experiment to check the two cheapest fixes** (a patched copy built in my scratchpad, not in the repo): `willReadFrequently: true` on the two texture canvases in `paintGasTexture`, and the `projectTags` sort using a plain `<` comparison. ABBA order, 4 loads each:

  | Case | Longest task, leader → patched | Total blocking time, leader → patched |
  | --- | --- | --- |
  | Projects 1280 4× | 254 → 130 ms | 339 → 148 ms |
  | Projects 375 4× | 227 → 134 ms | 325 → 156 ms |
  | Home 1280 4× | 150 → 139 ms | 186 → 151 ms |
  | About 375 4× | 125 → 118 ms | 134 → 128 ms |

  - **The texture task is gone:** what's left of the build is in steps of at most 61 ms.
  - **Task 1 is 10–25 ms shorter** on every page.
  - **Projects fps is unchanged:** GPU 4× at 375 and 1280 is 60/60 fps, main thread 44–57% on both builds (slow host period).
  - **The software path gains no fps,** because its 2D canvas is already read back cheaply.

**Recommended fixes, ranked by gain for effort**
1. **Projects gas texture: create the two canvases in `paintGasTexture` (`planets.ts`) with `getContext('2d', { willReadFrequently: true })`.**
   - **Gain (measured):** removes the 170–510 ms freeze on the first Projects visit at 4×, and roughly halves Projects' total blocking time (339 → 148 ms at 1280).
   - **Cost:** no fps cost. Two-line change.
   - **Why it works:** the drawing then happens on the CPU inside the existing per-band build steps, and `getImageData` is a plain copy.
2. **Software / slow-raster fallback: add a lower-resolution step before auto-pause.** The engine already drops from sharp to standard resolution when slow (V0.61). The proposal is one more step, e.g. `MAX_CANVAS_PIXELS` 1.1 MP → about 0.5 MP, before the V0.42 auto-pause.
   - **Gain (proxy):** halving the canvas pixels raised software 4× fps by about 1.6× (Home 13 → 22, About 10 → 16, Contact 9 → 14 in the slow period). A quarter of the pixels raised it about 3×. On today's numbers that would likely keep About, Contact, Behind the Scenes and Projects at 1280 above the auto-pause line on machines without GPU raster.
   - **Trade-off:** a softer background, which is dim and soft already.
   - **Effort:** medium (`backgroundEngine.ts`).
3. **`projectTags` sort: drop `localeCompare` at module load.** Use a plain comparison (check the tag order stays as wanted, because `<` is case-sensitive), or sort lazily in the Projects page with one `Intl.Collator`.
   - **Gain (measured):** 10–25 ms off start-up task 1 on every page at 4× (6–8 ms at 1×).
   - **Effort:** one line in `src/content/projects.ts`.
4. **Header: stop the second whole-document style recalc at start-up.** Write `--rail-width` somewhere that doesn't restyle the whole page, or do the reads before the writes in one layout effect.
   - **Gain (estimated from the trace):** about 10% of task 2 at 1280 (about 26 ms at slow 4×, likely 10–15 ms at normal 4×).
   - **Effort:** small to medium; V0.47/V0.56 timing must stay the same.
5. **Optional: split React's first render.** Rendering the root inside `startTransition` lets React yield every few ms during the render phase. The commit and the first layout stay one block.
   - **Gain (untested):** roughly half of task 2 could be split into short slices.
   - **Risk:** first paint could come a little later. Measure before adopting.
6. **Optional: Contact galaxy build: yield inside its first build step and between `paintBand` rows.**
   - **Gain:** 60–80 ms tasks drop under 50 ms.
   - **Value:** low; they run after first paint while the scene fades in.

Not worth doing: `putImageData` changes in other scenes (no stall anywhere), and splitting the scenes into their own chunk to speed up start-up (under 1% of task 1). No further work is needed for the GPU path: every page has at least 4× CPU headroom there.

**How I did it**
- **Builds and servers:**
  - `npm run build`, then `vite preview` on port 4761.
  - For attribution only: an unminified copy built into my scratchpad (`vite build --minify false --outDir …`) on port 4762.
  - The patched experiment copy on port 4763.
  - Playwright (`playwright-core` installed in my scratchpad only) driving the bundled Chromium 1208, headless.
- **GPU path:** `GALLIUM_DRIVER=d3d12`, `LD_LIBRARY_PATH=/usr/lib/wsl/lib`, `--enable-gpu --ignore-gpu-blocklist`. **Software path:** `--disable-gpu`. Each run logged the WebGL renderer string, so the path is never assumed.
- **Metrics** (`perf.mjs`):
  - **fps and frame time:** from a separate rAF loop's timestamps over 5 s.
  - **Frames over 35 ms:** intervals over 35 ms. This is close to the auto-pause line of 35.7 ms.
  - **Main-thread busy:** from a `toplevel` trace over the same window, as merged task time on `CrRendererMain` divided by the window. CDP's `TaskDuration` gave the same numbers within a few points.
  - The same trace gave compositor, Viz and GPU-process thread load. The script also timed the work inside rAF callbacks by wrapping `requestAnimationFrame`.
  - The Animation choice was set to `on` before load for all measured runs.
  - The auto-pause pass used no saved choice and recorded when `auto-paused` was written.
- **Why software 1280 4× is slow:** I traced 3 s of steady animation and summed main-thread self time:
  - Software 1280: 81–86% inside `CanvasResourceProviderSharedImage::ProduceCanvasResource`. That is the canvas flush, i.e. rasterising the frame's 1 MP of drawing. The scene's own JavaScript is 3–9%.
  - GPU path, same case: that flush is 2%.
  - Software 375: the canvas is small enough to be drawn directly on the CPU, so the cost sits inside the draw calls, and it still fits a 60 fps frame at 4×.
  - So at 1280 the work is raster, which DevTools' CPU throttle slows 4× along with the main thread. On a real machine with a GPU it runs on the GPU.
- **Why it was about 10 fps in V0.58 and here in the slow period:** the host's own speed. The same command gave 35 fps at 15:00 and 10–15 fps from 15:45 to 16:25, with WSL idle and nothing else of mine running. It recovered to 26–30 by 16:50. V0.58 also ran while other agents were benchmarking.
  - I could not reproduce V0.58's "main thread only 50% busy". Today both the trace and `TaskDuration` show 97–99% for software 1280 4×.
  - The same canvas-size sweep (1280 / 905 / 640 wide) shows software fps scaling with pixel count. That is the basis for recommendation 2.
- **Start-up attribution:**
  - `startup.mjs` traced cold loads (devtools.timeline) and listed every main-thread task over 50 ms with its children.
  - `profile.mjs` added a CDP CPU profile (200 µs sampling) of the unminified build and split each task's samples by function and by source module, using the bundle's `//#region` markers.
  - The profiler roughly doubles task lengths, so I only used it for shares. The durations in the start-up table come from runs without it.
  - `collator.mjs` timed the first `localeCompare` sort on a blank page.
- **Problem: host speed drifted mid-session.** I kept the normal-speed matrix as Table 1 and reported the slow-period numbers separately. I ran a software Home 1280 4× canary before and after each later pass, and compared the experiment only within interleaved (ABBA) runs.
