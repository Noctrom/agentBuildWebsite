### V0.33 — Snappier scene changes between pages
**Status:** in backlog · **Was:** D10 · **Suggested owner:** dev-1 · **Depends on:** — · **Drafted:** 2026-10-05

*As a visitor, I want the background to change as soon as I switch pages so that navigation feels quick and the old page's scene doesn't hang around.*

Chris finds page switches sluggish: the previous page's scene lingers into the new page. Two causes in `backgroundEngine.ts`: the crossfade is 1200ms, and the old scene stays fully visible until the new scene has finished building incrementally (S29/S31), which adds more delay before the fade even starts. This replaces the "crossfade smoothly" behavior from S26.

- [ ] On navigation, the old scene starts fading out immediately (not after the new scene is ready) and is gone within ~250ms
- [ ] The new scene fades in quickly (~250ms) as soon as it's ready; while it builds, only the plain space background shows (no old scene, no flash of a bright or empty white frame)
- [ ] Quickly clicking through several pages never shows a stale scene and never stacks multiple scenes; only the latest page's scene ends up visible
- [ ] Reduce motion: scene swaps instantly, as today
- [ ] Still smooth on a mid-range phone (no jank introduced); `npm run build` and `npm run lint` pass

**Open questions:** None.

### V0.34 — Version numbers and batched docs
**Status:** in backlog · **Was:** D11 · **Suggested owner:** leader · **Depends on:** S33 merged (no story in flight during the move) · **Drafted:** 2026-10-05

*As Chris, I want stories numbered as versions and the docs filed in batches of 25 so that the backlog, inbox and logs are easy to read and browse as the project grows.*

Chris wants to replace the S and D ids with one version sequence. Each story is +0.01 (S1 → V0.01). Files are grouped in batches of 25, and each whole number gets its own folder. This story becomes **V0.34** under the new scheme. Chris's decisions:
- **Batch boundaries:** a whole number starts a group. `v0/` holds `v0.00-v0.24`, `v0.25-v0.49`, `v0.50-v0.74`, `v0.75-v0.99`; V1.00 opens `v1/` (`v1.00-v1.24`, …). V0.00 is the starting point, not a story.
- **History is renumbered:** S<n> → V0.<nn> (S7 → V0.07, S33 → V0.33). A mapping table keeps the old S and D ids. Past commit messages keep their old `S7:` prefixes; published history is never rewritten.
- **The story-writer assigns versions:** a story gets the next free version when Chris approves it (status `ready`). Unapproved drafts have no number yet. If the leader splits a story, the extra parts take the next free versions.
- **Logs:** one file per story, named `v0.07-about-page.md`, with the agent named inside.

Target layout:
```
BACKLOG.md                      # index only: status legend, one table row per version linking to its details, mapping table (old S/D → V)
docs/backlog/v0/v0.00-v0.24.md  # full story text, V0.01–V0.24
docs/backlog/v0/v0.25-v0.49.md
docs/story-inbox/drafts.md      # unnumbered drafts still being discussed with Chris
docs/story-inbox/v0/v0.25-v0.49.md   # stories as Chris approved them
docs/agent-logs/v0/v0.00-v0.24/v0.07-about-page.md
```

- [ ] All S ids renumbered to versions across the backlog, logs and docs; mapping table (S id, original D id where there was one, V id, title) in `BACKLOG.md`
- [ ] `BACKLOG.md` becomes a short index; story details live in the batch files under `docs/backlog/`
- [ ] Existing `docs/agent-logs/dev-1.md` and `dev-2.md` split into one file per story in the right batch folders, content unchanged apart from ids; old files removed
- [ ] Story inbox moved to `docs/story-inbox/` as above. Approved stories stay in their batch file after triage with status `in backlog` (a record of what Chris approved) instead of being deleted
- [ ] New-story conventions updated everywhere they're defined (`CLAUDE.md`, `.claude/agents/dev-1.md`, `dev-2.md`, `story-writer.md`): branch `story/v0.34-<slug>`, commit prefix `V0.34:`, log file path and name, who assigns versions, and when to start a new batch file or whole-number folder

### V0.41 — Animation on/off control in the footer
**Status:** in backlog · **Suggested owner:** dev-1 · **Depends on:** — · **Drafted:** 2026-10-05

*As a visitor, I want a small control in the footer to turn the background animation on or off so that I can choose motion regardless of my device's defaults.*

Today reduced motion comes only from the OS setting. This adds a site-level choice that applies to all page scenes. V0.42 needs it so visitors can undo the automatic low-power pause. Chris's choices: the control goes **in the footer**, and a visitor's explicit choice **overrides the OS setting** in both directions.
- [ ] A small, unobtrusive control in the footer, labelled for its purpose (e.g. "Animation: on/off"), on every page at 375px and desktop widths
- [ ] Turning it off makes every scene static, the same as OS reduced motion. Turning it on resumes animation.
- [ ] The visitor's choice overrides the OS setting: with OS reduce-motion on, choosing "on" animates the scenes. With the OS setting off, choosing "off" stops them.
- [ ] The choice is remembered on that browser across visits and page changes (stored locally; no backend)
- [ ] With no saved choice, the site follows the OS reduce-motion setting as it does today
- [ ] The control is keyboard-usable, has a visible focus state and an accessible name, and its on/off state is announced to screen readers
- [ ] Works at 375px and desktop widths

**Open questions:** None.

### V0.42 — Auto-pause animation on low-powered devices
**Status:** in backlog · **Suggested owner:** dev-1 · **Depends on:** V0.41 · **Drafted:** 2026-10-05

*As a visitor on a low-powered device, I want the site to switch animation off automatically and tell me why so that the page stays smooth and I can turn it back on if I want.*

Chris: if the device can't keep up, switch to reduced motion automatically, let the visitor change it, and show a small unintrusive message explaining what happened and why. Detection is based on how smoothly the animation actually runs, not on guessing the device type. Chris wants the automatic pause **remembered** across visits; the visitor can turn animation back on with the V0.41 footer control at any time. Message text approved by Chris as written below.
- [ ] If the background animation runs consistently slow on a page (below ~30 frames per second for about 3 seconds), the site switches animation off
- [ ] Testable: in Chrome DevTools with CPU throttling at 6× slowdown the switch happens; with no throttling on a normal desktop it does not
- [ ] When it happens, a small message appears in a corner, without covering page content at 375px: "Animation paused to keep things smooth on this device." with a "Turn back on" button and a close button
- [ ] The message closes on its own after about 10 seconds or when closed. "Turn back on" re-enables animation via the V0.41 setting, and the footer control reflects the change.
- [ ] The automatic pause is remembered on that browser across visits. Detection doesn't run again and the message doesn't reappear, and the footer control shows animation as off.
- [ ] Auto-detection never overrides a choice the visitor made: if they turned animation back on (with the button or the footer control), it is not switched off again on later pages or visits
- [ ] The message is announced politely to screen readers and does not steal focus
- [ ] Detection does not run when animation is already off (OS setting or visitor choice)
- [ ] Works at 375px and desktop widths

**Open questions:** None.
