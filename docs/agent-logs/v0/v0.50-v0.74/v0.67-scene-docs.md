**Agent:** dev-2

**What I did**
- The Brightness section in `src/scenes/types.ts` now describes both views:
  - Normal: opacity 0.2, DPR capped at 1.
  - Hidden content: opacity 1. Native DPR capped at 3840×2160 backing pixels, but not on phones, which get full strength only. A silent drop back to the normal resolution if sharp mode runs slow. Fades with the content, or switches at once with reduced motion.
- The `SceneSize.dpr` comment describes both caps and points to the new "Size changes between the views" section. That section says the engine rebuilds the scene in the background when the size changes.
- `SceneBudget.maxOpacity` notes that it stays 0.2 while the canvas is shown at 1.
- New note for scene authors: build for full strength. Soft layers must show no banding or blockiness: bake at enough resolution, dither long gradients, and check a new scene with content hidden at DPR 2.
- Comments only. No code changed.

**How I did it**
- Checked each claim against `backgroundEngine.ts` (`MAX_DPR`, `MAX_CANVAS_PIXELS`, `MAX_SHARP_PIXELS`, `measure`, `setShowcase`, `applySize`, `startRebuild`/`finishRebuild`), `SpaceBackground.tsx` (`isPhone`) and the V0.61 log. I only read these files.
- How the rebuild affects scene authors:
  - When the view switches while the scene animates, the engine calls `create` again for a new instance. It does not call `resize`.
  - It runs one priming draw off screen, swaps the canvases and disposes the old instance. `frame.time` carries on.
  - So the Lifecycle text no longer says `create` runs "once". The docs ask that `create` give the same picture as `create` + `resize`, and that it use a fixed seed. No scene uses `Math.random` today.
- A real resize, or any change with reduced motion on, still calls `resize` at once. The docs say so.
