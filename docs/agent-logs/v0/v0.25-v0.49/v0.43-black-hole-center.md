**How I did it**
- `layoutFor(size, railWidth)`: `rail = width >= 1024 ? railWidth : 0`, `top = width >= 1024 ? 0 : 64`, and the centre is the middle of the area that is left. `r = max(24, 0.08 × min(areaW, areaH))`, capped so the disk (4.8r each side) always fits within the area's width.
- The rail width comes from `document.documentElement.style.getPropertyValue('--rail-width')`. That is the inline style the Header sets (V0.47). Reading an inline declaration doesn't force style or layout, so it is cheap enough to do on every frame. The scene contract says scenes don't touch the DOM. This only reads one published value, and the comment in the code says so.
- The scene follows rail changes (`followRail()` in `draw`). After a client-side navigation, the Header's ResizeObserver publishes the new rail width (98 → 187) one rendering step *after* the scene is created, so the first frame may use the old value. It corrects on the next frame, while the scene is still fading in. Sprites are rebuilt only if the radius changes.
- I left `BehindTheScenes.tsx` alone (dev-1 is on V0.55 there).
- Notes for V0.44 / V0.45 (same file):
  - The layout lives only in `layoutFor`; the draw code uses `layout.cx/cy/r`.
  - The disk layer re-renders at `DISK_FPS` 12. Faster spin and hot spots probably need a higher rate or a per-frame overlay.
  - An orbiting planet should orbit `(cx, cy)` and scale with `r`. It must also stay inside `areaWidth`; the disk already uses up to 96% of it at 375.
  - The page's AA margin is set by the budget, not by position. Bare body text is lowest at 5.31 with the hole fully bright, so brighter effects can't break AA, but keep the scan.
