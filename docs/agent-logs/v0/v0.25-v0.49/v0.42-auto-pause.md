# V0.42 — Auto-pause animation on low-powered devices (2026-10-05)
**Agent:** dev-1
**Branch:** story/v0.42-auto-pause · **Status:** done

**What I did**
- If the background animation runs consistently below ~30 fps for 3 seconds, the site saves `auto-paused` with the V0.41 store, and the scenes go still.
- Tested with DevTools CPU throttling over CDP. At 6x on a 1280 desktop it pauses (measured 18.7 fps average, 20 fps median). Without throttling it never pauses, across all routes and the 404 (56.7 to 60 fps).
- A glass toast appears in the bottom corner with Chris's text, "Animation paused to keep things smooth on this device.", plus a "Turn back on" button and a close button (x, named "Close message").
- The toast closes on its own after about 10 s (measured 9.9 s). It also closes with the x or Escape. The timer pauses while the toast is hovered, focused or in a hidden tab. "Turn back on" saves an explicit `on`, and the footer switch shows On.
- The pause is remembered. After a reload: no toast, the footer shows Off, and detection doesn't run.
- A visitor's own choice is never overridden. After "Turn back on" or the footer switch, the site stays `on` at 6x across navigation and a reload.
- The toast is a `role="status"` / `aria-live="polite"` region that is always in the DOM, so the message is announced when it is filled. It never takes focus.
- Detection doesn't run when animation is already off: not with a saved `off`, not with OS reduce motion, and not after an auto-pause.
- Works at 375 and 1280.

**How I did it**
- New `frameRateMonitor.ts` holds the logic, with no DOM access. A frame counts as slow if its interval is over 1000/28 ms (35.7 ms). It fires once if at least half of the frames in the last 3 s were slow. Before it starts measuring, it needs 1 s of warm-up and then a full 3 s window of steady frames.
- Why 28 fps and frame counting: frames land on vsync (16.7, 33.3 or 50 ms), so this line falls between 30 and 20 fps frames. A device capped at 30 fps, such as Chrome's battery saver, is not "slow". Counting frames instead of averaging time means a single long stall (GC, another app) can't trip it.
- `BackgroundEngine.watchFrameRate(onSlow | null)` feeds the monitor the real rAF intervals from its tick. A scene's own draw rate (the black hole's 12 fps disk) doesn't matter. Only steady frames count: no scene build pending, no fade running, tab visible. Anything else resets the monitor, and so do `setScene` (route change), `setReducedMotion`, resize and every loop (re)start (hidden tab, idle, paused).
- `SpaceBackground` turns watching on only while `useMotionChoice() === null` and animation is on. When the monitor fires, the callback checks the store again (another tab may have saved a choice), then calls `setMotionChoice('auto-paused')` and `onAutoPause`.
- `Layout` keeps the toast's open state, which lasts only for this page session, so it never reappears on a later visit. The toast is shown only while the choice is still `auto-paused`, so turning animation on from the footer closes it too.
- Placement: `AutoPauseNotice` is `position: sticky; bottom: 0` after the footer. While the page scrolls it sits in the bottom-right corner. Scrolled to the end it takes its own space below the footer, so the footer and the animation switch stay fully visible. It never reaches the top bar.
- The toast's height is published as `--notice-height`, which feeds the new `scroll-padding-bottom`, so focused elements scroll clear of it.
- Styling uses the `bg` glass (darker, for legibility over text), `glass-edge`, a border and the secondary Button.
- If it closes with focus inside, focus moves to `<main>` (preventScroll) so it isn't lost.

**Follow-ups**
- At 375, while the page is mid-scroll, the toast overlays whatever content is behind the bottom corner for up to 10 s, as any corner toast would. It never covers the top bar or the footer, and focused elements scroll clear of it. If Chris wants zero overlap, the alternative is an in-flow banner.
- The hidden-tab case is covered by the code (the loop stops on `visibilitychange`, and a restart resets the monitor). I did not emulate it in headless Chromium.
- Headless Chromium on this machine ran some desktop scenes at about 30 to 37 fps unthrottled in one baseline run, still above the 28 fps line. A real GPU desktop should be faster.
