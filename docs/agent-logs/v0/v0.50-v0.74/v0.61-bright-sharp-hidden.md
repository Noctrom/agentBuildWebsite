# V0.61 — Hidden-content view shows the background bright and sharp (2026-10-07)
**Agent:** dev-1
**Branch:** story/v0.61-bright-sharp-hidden · **Status:** done

**What I did**
- Full strength: while content is hidden the scene canvas goes from opacity 0.2 to 1, 5 times brighter. Showing content again returns it to 0.2.
- Native resolution on desktop: while hidden, the canvas backing size is its on-screen size × `devicePixelRatio`. Measured at 1280×800 with DPR 2 on all 7 routes: 2560×1600, or 2530×1600 where a 15 px scrollbar narrows the page to 1265 px. It goes back to 1×.
- Showing content again by button, Esc or background click restores strength and resolution. All three ways were tested.
- With animations on, the brightening and dimming fade with the content: same 300 ms, close to the same ease-out. Sampled mid-fade: background 0.55 / main 0.56. With the switch off, auto-paused, or OS reduce motion, both switch instantly (checked at 30 ms).
- A paused scene (switch off, auto-paused, OS reduce) also shows its frozen frame bright and sharp. Two screenshots 600 ms apart are identical.
- Phones get brightness only (decision and measurements below).
- If sharp mode runs slow, the engine silently drops to the standard resolution and keeps full strength. Only after that can V0.42's auto-pause trigger. Tested: drop after about 4 s, no saved choice, no toast. Then at 8x throttle, auto-pause followed with the background still at full strength.
- Eye button: while hidden it sits on a dark glass disc, so it passes AA over the brightest frame. The focus ring stays visible (screenshot `focus-hidden-1280.png`).
- Every page's scene works: Home, About, Projects, Resume, Contact, Behind the Scenes and 404 at 1280 DPR 2. Phones were tested on `/` and `/contact`.
- Works at 375 and 1280. No horizontal overflow at either width.

**How I did it**
- `BackgroundEngine.setShowcase(on)` is called from `SpaceBackground` (new `showcase` prop, which Layout sets to `contentHidden`).
  - Strength: a fully shown layer's opacity is `layer.opacity × strength`, not `× BACKGROUND_MAX_OPACITY`. Strength is animated in the rAF loop (300 ms, cubic ease-out) and set at once with reduced motion. `paintCopy` (the V0.48 mirrors) uses it too. The scenes' `budget` stays 0.2: no scene reads it, and it describes the normal cap.
  - I animated it in the engine rather than with a CSS opacity transition on the container. Group opacity would differ from per-layer opacity during scene crossfades and break the mirrors' pixel match.
- Sharp: `measure()` drops the DPR cap and uses `MAX_SHARP_PIXELS` (3840×2160, a 4K panel) in place of the 1.1 M cap. When uncapped the device ratio is kept exact rather than rounded, so the canvas really is size × DPR.
- Hitch: a scene's `resize` rebuilds every cache at once. Measured `resize` + first draw at DPR 2: the sun took 35+28 ms at 1x and 177+48 ms at 4x, the black hole 29+7 ms at 4x, the others ≤ 33 ms. On About that showed as a 150–233 ms frozen frame at the start of the fade.
  - Fix: for showcase changes while animating, the engine now makes a new instance of the shown scene at the new size in the background, in separate tasks between frames. First `create`, which for generator scenes (sun, nebula) runs in the same 6 ms slices as a scene change. Then one priming draw on an off-screen canvas. The next rAF swaps the canvases (`replaceWith`), so there is never an empty frame.
  - The old instance animates meanwhile. Layers now carry their own `size`, so a layer fading out can stay at its old resolution.
  - A real viewport resize, or a still frame, still resizes at once, and now always redraws right after (previously an animated resize could show one cleared frame).
- Fallback: a second `FrameRateMonitor` runs only while sharp mode actually adds pixels. While it runs, the V0.42 monitor is reset each frame, so the drop always comes first. When it fires, `sharpBlocked` is set for the rest of the page session and the shown layer is rebuilt at standard resolution. Decision: this check also runs when the visitor chose "on". It only lowers resolution and never pauses, so it doesn't override their choice.
- Phones: `isPhone()` in SpaceBackground means `(pointer: coarse)` and a screen short side under 600 CSS px. Tablets and desktops get sharp mode, with the fallback as a safety net.
- Button AA: while hidden, `HideContentButton` adds `bg-bg-glass` plus a 6 px `bg-glass` box-shadow ring (`backingClass`). The 2 px outline at 2 px offset falls inside it. On focus the glow is added outside. No size or layout change.

**Phone decision (375, 4x CPU throttle)**
| setup | standard (content shown) | sharp (hidden) |
|---|---|---|
| software raster, DPR 3, mobile emulation, run 1 / run 2 | 58.3 / 57.2 fps | 8.3 / 8.7 fps, 100% slow frames |
| software raster, DPR 2, run 1 / run 2 | 59.9 / 60.0 fps | 20.4 / 21.6 fps, 67–76% slow |
| real GPU (RX 7800 XT via WSL D3D12), DPR 3 and 2 | 60 fps | 60 fps |

CPU throttling doesn't slow the GPU, and a phone GPU is far weaker than a desktop card. So I took the software-raster run as the stand-in for a phone's fill rate; it is the same setup the MAX_DPR comment was based on. That shows clear stutter, so **phones get brightness only**.

**Desktop (1280×800, DPR 2)**, mean over 7 routes:
- Real GPU, 1x: 55.3 fps shown / 55.5 fps hidden.
- Real GPU, 4x: 54.4–54.8 / 54.2–54.7 fps.
- All routes hold 60 fps except Contact (below).
- With no GPU (software raster): 21 fps sharp at 1x. That is what the fallback covers.

Repeated runs differed by about ±2 fps. dev-2 was running V0.59 benchmarks at the same time (load average 4.6–5.9).
